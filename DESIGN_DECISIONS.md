# Design Decisions

Ключевые архитектурные решения проекта (задание 2) и их обоснование.

## 1. Почему HashEmbedder

Офлайн-эмбеддер нужен, чтобы тесты и демо-сценарии работали быстро,
детерминированно и без сети, без каких-либо ключей и обращений к API GigaChat.
`HashEmbedder` хэширует признаки слов в плотный вектор и даёт стабильное
поведение независимо от доступности сервиса эмбеддингов. При наличии
`GIGACHAT_CREDENTIALS` в живом режиме подставляется настоящий
`GigaChatEmbedder` (обёртка над `GigaChatEmbeddings`), а `HashEmbedder`
остаётся эталоном для офлайна и гоняющих без ключей окружений.

## 2. Почему RRF с выбранными константами

Слияние выдач BM25 и dense-поиска сделано методом Reciprocal Rank Fusion.
Классический рекомендованный параметр из литературы — небольшие значения
вокруг 60; многие промышленные реализации берут значительно больше (например,
5860 — значение по умолчанию в `fusion.reciprocal_rank_fusion`). На маленьком
корпусе (десятки документов) слишком большое k «сглаживает» вклад второй
выдачи, поэтому в сервисе используется эмпирически подобранное k=620: оно
сохраняет вклад и лексического, и семантического канала и при этом не
забивает точное совпадение по идентификатору документа (там вклад усиливает
дополнительный лексический буст `boost_exact_identifiers`).

## 3. Почему эмбеддинги создаются без явного model

Попытка передать в `GigaChatEmbeddings` модель `EmbeddingsGigaChat` приводила
к ответу сервера 404 «No such model» (личный scope аккаунта), при этом
рабочий вызов оказался именно без параметра `model` — SDK подставляет
корректное имя. Поэтому `get_embeddings` опускает `model`, если `EMBED_MODEL`
не задан явно или равен «EmbeddingsGigaChat». Такое поведение зафиксировано в
коде и комментарии к `.env.example`.

## 4. Планы: InMemoryStore -> SqliteStore для персистентности

Сейчас кратковременная память живёт в `MemorySaver`, а долговременная — в
памяти процесса с промежуточным снимком в JSON (`MEMORY_FILE=memory_dump.json`)
между перезапусками. План — заменить долговременное хранилище на
`SqliteStore` (LangGraph), а при многопроцессном/многомашинном развёртывании —
на PostgreSQL-совместимый `Store`. Это уберёт необходимость ручного снимка,
даст единую точку хранения для профилей и аудита и сохранит данные при
перезапуске сервера.
