# Диалоговый агент с памятью и гибридным поиском (задание 2)

Индивидуальный проект курса «Продвинутая разработка и тестирование ИИ-агентов».
Каркас диалогового агента на **GigaChat + LangGraph**: пользователь сообщает
реквизиты по частям, перебивает посторонними вопросами и возвращается к теме
через десяток реплик; агент собирает структурированные слоты, ищет документы в
базе знаний и отвечает строго со ссылкой на источник, а про собеседника копит
долговременную память, которая переживает сессию.

Предметная область — поддержка дев-облачной платформы (тарифы, квоты воркеров,
уведомления, экспорт отчётов, возврат). Она выбрана сознательно: она же лежит в
основе файла `../dialogs.jsonl`, поэтому сценарии из выданных диалогов легко
переносятся на этого агента для тестов и скринкаста.

## Как устроено

Линейный контур диалога (LangGraph `StateGraph`):

```
user message
  -> extract_slots    structured output (SlotUpdate), слоты копятся в state
  -> manage_context   бюджет контекста: фактические токены + суммаризация
  -> build_profile    достаёт долговременную память пользователя (recency-взвешенно)
  -> respond          LLM вызывает инструмент search_knowledge (гибридный поиск),
                      ответ обязан ссылаться на источник [NN-Б vN]
  -> persist_user     новые слоты уходят в долговременную память + зеркало в Store
```

Компоненты:

| Слой | Файлы | Назначение |
|---|---|---|
| Граф | `src/graph/build.py`, `src/graph/nodes.py` | Контур, checkpointer, Store |
| Слоты | `src/models.py` | Схема structured output |
| Контекст | `src/context.py` | Бюджет токенов, суммаризация выпавшего окна |
| База знаний | `src/kb/catalog.py`, `src/kb/seeds.py` | Документы с редакциями и периодами действия |
| Гибридный поиск | `src/rag/*` | BM25 + эмбеддинги, RRF, реранк, `@tool` |
| Память | `src/memory/*` | Схема, горизонты, конфликты, аудит, удаление, recency, консолидация |

## Установка и запуск

Нужны Python 3.11+ и `uv`.

```bash
cp .env.example .env      # вписать GIGACHAT_CREDENTIALS для живого режима
make install              # uv sync (база + dev + GigaChat-экстра)
make test                 # офлайн-тесты без сети и без ключей
```

Живой диалог с настоящим GigaChat:

```bash
make run                  # консольный диалог (пример: "какой лимит воркеров у Start?")
```

Офлайн-демонстрации (подходят для скринкаста без сети):

```bash
make demo-temporal        # критерий 4: один вопрос, две даты -> разные корректные ответы
make demo-budget          # критерий 2: бюджет токенов и суммаризация на длинном диалоге
make demo-memory          # критерии 5-6: память по образцу dialogs.jsonl, аудит, удаление
make consolidate          # критерий 6: фоновая переработка памяти вне диалога
```

Всё обязательное работает офлайн: поиск на встроенных семенах БЗ и HashEmbedder.
GigaChat подключается автоматически при наличии ключей (`make run`), эмбеддинги —
через `GigaChatEmbeddings`; реранкер cross-encoder включается, если установлен
экстра `rerank`.

## Способ проверки

- `make test` — зелёные автотесты по всем шести критериям (дубль модели из
  `tests/fakes.py`, сеть и ключи не нужны).
- `make demo-temporal` — печать: на `2025-12-05` Start даёт лимит 5 воркеров,
  на `2026-06-10` — 10; в обоих случаях корректная редакция.
- `make demo-memory` — три «сессии», смена тарифа (UPDATE), поиск по свежести,
- `make demo-budget` — длинный диалог (33 реплики пользователя) прогоняется через RollingSummaryPipeline: видны срабатывания сжатия, экономия токенов и сводка ключевых фактов после суммаризации.
  удаление по запросу с маскированием обязательных платежей, журнал аудита,
  консолидация.
- Скринкаст: `make test`, затем живой диалог через `make run` с 1-2 поисками по
  БЗ и ссылкой на источник, затем офлайн-демо и «память через сессии».

## Связь с dialogs.jsonl

Файл `../dialogs.jsonl` (24 клиента, по 3 сессии на клиента: дни 1, 5, 12)
описывает ровно те механики, которые тренирует задание 2: факты сообщаются в
ранней сессии и вспоминаются позже («работаю из Сочи», «Адрес тот же»), часть
сведений меняется («перешёл на Enterprise», «уже на Start»), есть персонализация
(email-дублирование, отпуск, пуши). Этот каркас уже понимает такую предметную
область (тарифы Start/Pro/Enterprise, проекты PRJ-*, уведомления), поэтому
реплики из dialogs.jsonl можно использовать как рукописные тест-кейсы и для
скринкаста. Полный разбор пригодности файла — в отчёте преподавателю.

## Что важно знать про каркас

- Память между сессиями живёт в процессах реестра (`InMemoryStore` и
  `MemoryEngine`). Для продакшена замените на `SqliteStore`/PostgreSQL-store и
  сохраняйте состояние под thread_id (Roadmap).
- Контроль ссылки: правило «ответ обязан содержать тег [NN-Б vN]» зашито в
  SYSTEM_GUIDE и проверяется в тесте контура (`test_graph_contour.py`); в
  живом режиме при желании можно добавить валидацию последнего ответа.
- Источник конфигурации: `.env` (бюджеты токенов, `DEFAULT_AS_OF`, модели).

## Дорожная карта доработок (по желанию)

1. Долговечное хранилище: `SqliteStore`/Postgres вместо `InMemoryStore`;
2. `bm25s` + лемматизация pymorphy3 вместо компактного BM25;
3. Qdrant как векторная БД (native `Fusion.RRF`, payload-фильтры по датам);
4. cross-encoder реранкер через экстра `rerank`;
5. расширенная база знаний — свои документы/редакции и больше точек временно́го
   расхождения;
6. режим REST (FastAPI) и cron/CI-хук для `make consolidate`.
